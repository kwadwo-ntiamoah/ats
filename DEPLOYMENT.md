# Building the `deploy/` folder

`deploy/` is a generated, git-ignored artifact — a self-contained IIS deployment
package built from Next.js's "standalone" output. Regenerate it with the steps
below whenever you need a fresh build to ship.

See `deploy/DEPLOY-NOTES.txt` (inside the generated folder itself) for how to
actually install and run the package on the IIS server — this file only covers
producing the folder.

## Steps

1. **Build the app**, from the `sidi-web/` project root:

   ```
   npm run build
   ```

   This produces `.next/standalone`, `.next/static`, and uses the existing
   `public/` folder.

2. **Replace the generated parts of `deploy/`** with the fresh build output.
   Do **not** touch `deploy/web.config` or `deploy/logs/` — those are
   environment-specific (API credentials, IIS settings, runtime logs) and are
   not regenerated by the build.

   ```
   rm -rf deploy/.next deploy/node_modules deploy/public deploy/server.js deploy/package.json
   cp -r .next/standalone/. deploy/
   mkdir -p deploy/.next/static
   cp -r .next/static/. deploy/.next/static/
   cp -r public deploy/public
   ```

   After this, `deploy/` should contain: `.next/`, `node_modules/`,
   `public/`, `package.json`, `server.js` (all freshly generated), plus the
   untouched `web.config`, `logs/`, and `DEPLOY-NOTES.txt`. Per
   `DEPLOY-NOTES.txt`, this whole folder is what gets copied to the server —
   nothing further needs to be packaged or zipped.

3. **Sanity check** before shipping: confirm `deploy/web.config` still has the
   correct `API_BASE_URL` / `API_CLIENT_ID` / `API_CLIENT_SECRET` for the
   target environment — rebuilding never changes this file, so if it was
   already correct it stays correct, but it's worth a glance since a stale
   value here is a common source of "invalid link" errors after deploy.

## Why `web.config` and `logs/` are preserved

- `web.config` holds per-environment secrets and IIS process settings that
  have nothing to do with the app's build output — regenerating it from
  scratch would blow away real credentials in favor of the dev-default
  placeholders.
- `logs/` is where the running app writes `app.log` at runtime (see
  `DEPLOY-NOTES.txt`); it isn't part of the build and should carry over
  between deploys so history isn't lost.
